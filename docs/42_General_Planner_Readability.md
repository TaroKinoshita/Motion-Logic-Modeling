# 共通生成の読みやすさと入力範囲

## 今回の変更

文書41の共通生成処理を拡張した。場面ごとの座標は入力しない。同じ関数が、語の文字数・時刻・強調から配置と変形キーを作る。

- 本文の最低フォントサイズを映像高さの4.5%に設定した。`minFontHeight`で変更できる。これは設計上の初期値で、読みやすさの実証値ではない。
- 左右・上下・段階配置に、語順通りの縦配置を加えた。文字サイズ不足と衝突は候補を棄却し、読む順の逆転と前行の構図の繰り返しには減点する。
- どの候補も条件を満たさない場合は422を返す。文字を縮め続けず、行の分割または同時表示語数の削減を求める。行を自動分割する処理は未実装。
- 次の語がすぐ出る場合、前行の主役を持ち越さない。登場前に3コマ以上空き、前行との間隔と保持文字のサイズが条件を満たす場合だけ短時間保持する。`continuity: none`で無効にできる。
- 語間隔と構図に応じて、横から収束・下から収束・切り替えて保持を選ぶ。移動は共通のcubic曲線を使う。曲線の形、テンプレート、点数の重みは手で定めたもの。
- 本文の衝突とはみ出しを全コマで検査し、問題があれば保存前に停止する。検査上限は7200コマ。
- 語の表示時間が文字数に対して短い場合に注意を記録する。1秒あたり16文字は暫定値で、発音の速さや読了を測ったものではない。1コマだけの表示も注意を出すが拒否しない。
- アプリの生成結果に、検査コマ数、構図、動き、持ち越し理由、表示時間の注意を表示する。

観察と設計を混同しないため、入力・候補の点数・選択理由・検査結果・設計値である旨を生成先のadaptation文書に保存する。元のプロジェクトは変更しない。

## 実行した確認

`Test_audio1`の元歌詞と、文字数を変えた別歌詞を同じ処理で生成・書き出しした。各336コマ、30fps。比較動画は2560×720で音声を含む。ffprobeで336コマを確認した。2つのシーンを全コマ検査して、文字同士の重なりとはみ出しはどちらも0件。同一入力で同一シーンになることも確認した。

確認コマでは、強調した語の大小差、左右・上下の構図の変化、別歌詞に応じた配置変更を確認した。コマ一覧だけで動きや歌声への同期が良いと評価することはできない。

入力範囲の検査は、語数1/2/4/8、1語の文字数1/5/15/50、強調位置が先頭/末尾の32条件。同じ位置になる語数1の条件も別実行として含むため、32件の独立した素材ではない。24条件で生成し、8条件は最低文字サイズを守れないため拒否した。前行の保持・保持無効・次の語が即時登場する場合も検査した。文字列は繰り返しの「風」であり、実際の語義・多言語・全書体を検証したものではない。

既存32テスト、型検査、Webビルドが合格。APIは接続済みだが、この作業でのHTTP経由とブラウザ操作は未検証。生成関数・保存・描画・書き出しの検証であり、完成品質の受け入れ試験ではない。

## 残る品質の問題

入力時刻は仮合わせで、歌声とのアライメントはしていない。強調語も入力で指定する。作家から学習した構図・運動の選択ではなく、作家判定の成立を示すものでもない。今回改善したのは、異なる歌詞にも同じ制約を適用して配置を作り、成立しない理由を返す仕組み。

次は語の発音時刻の確認、主役の登場前後を含む語群全体の動き、横つぶれ・回転・停止の長さの選択を共通処理へ組み込む。背景反転はいまも行番号の周期で、音や内容から決まっていない。衝突0だけを目標にすると安全で単調な構図になるため、構図の良さと緩急は別途動画で評価する必要がある。
