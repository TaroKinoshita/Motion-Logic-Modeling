# 動きの型を使った歌詞映像の生成計画

次の成果物は、Lyricsample1から採った流し込み・タメ・横つぶれ・回転と、主役と脇役の大きさの関係を、新しい歌詞に適用できる編集可能なシーン。初回は同じ合成音源と歌詞で、現行の時刻規則を基準にして、動きと配置が見た目にどう効くかを比較する。追加作品、発音資料、別の実曲での検証は最後に回す。

## レビューと現状

- `lyric-generation.ts` の `entrance` は固定の縦移動、`hold` はその開始待ちで、拡縮・回転・せん断や、動画から計測した曲線を入力に取らない。`stagger`・`invert`・`combine` も時間パラメータと所定の描画処理を使う。新しい実曲への受け入れは未実施。現行の生成比較は合成音源で行った。
- 全編モデルの1,866キーはすべて変形キー。トレースは変形1,542と外形1,353で合計2,895。圧縮では総数と、演出を扱う単位あたりのキー数を両方記録する。2フレーム以下のブロックは101個。自動接続は1組だった。
- 6Fの0.361は、代表輪郭1個の試行で「各」を対象に測定した値。最新版の0.689は全画面の値。同じ対象の箱と同じ二値化条件で測り直して、強いつぶれの改善を判断する。
- Fast SpriteとVTracerはローカルで実測済み。OmniLottieは公式のGPU使用量15.2Gと対応を調べた。8GB機での実行結果は得ていない。今回の初回は共通シーン、既存の曲線近似と描画系で進める。 [ローカルの技術記録](18_Vectorization_Tools.md)・[全編の実測](19_Editable_Motion_And_Style_Plan.md#8-全183コマの編集モデル)・[OmniLottie公式実行条件](https://github.com/OpenVGLab/OmniLottie#4-inference)

## 研究から採る設計

- KovarとGleicherは、人のモーションキャプチャから似た運動区間を抽出してパラメータ化している。MLMでは小標本から始め、動きの開始・着地・停止・極値を合わせた区間を人が確認する。事例が増えてから同じ種類の曲線のばらつきを比較する。 [Automated Extraction and Parameterization of Motions in Large Data Sets](https://graphics.cs.wisc.edu/Papers/2004/KG04/)
- Fast Spriteは映像をスプライトと時間方向の変形で表す。OmniLottie論文のLottieレイヤー整理も、時刻、階層、変形、文字や輪郭を独立に扱う。MLMでは現行シーンを共用しつつ、元映像の観察に紐づく曲線だけを新しい文字に適用する。 [Fast Sprite Decomposition](https://arxiv.org/abs/2408.03923)・[OmniLottie論文 §4.1](https://openaccess.thecvf.com/content/CVPR2026/papers/Yang_OmniLottie_Generating_Vector_Animations_via_Parameterized_Lottie_Tokens_CVPR_2026_paper.pdf)
- ルビは親文字または文字列に対する注釈として扱う。本文の字ごとの分割には書記素を使い、単字の読みと、複数文字に一つの読みを付ける場合を扱う。 [W3C CSS Ruby Layout](https://www.w3.org/TR/css-ruby-1/)・[Unicode Text Segmentation](https://www.unicode.org/reports/tr29/)

### 型が保持する内容

1. 出典は作品ID・版・ブロックID・元のコマ範囲・観察し直した状態。接触やカットをまたぐ場合はイベントを別に参照する。
2. 曲線の時間は0〜1に揃える。移動は基準となる位置からの符号付き差分で持ち、画面幅・高さまたは墨付きの寸法に対する比と元の振幅も記録する。回転は連続する角度差、つぶれは基準幅に対する倍率、着地と停止は区間内の時刻を持つ。往復のように開始と終了が同値でも動きを保持できるようにする。
3. 適用先には文字・行・親グループの区別と、基準アンカー、開始時刻、元の秒数または拍数、許容振幅、文字数を変えた際の配置と時差の扱いを持つ。新曲で拍指定を使う場合はその音源の拍位置で展開する。生成結果から使った版と値を追えるようにする。
4. 観察、再利用する型、型を選択する規則を識別して保存する。初回は人がタイプと適用先を選ぶ。作品が増えたら、同じイベントに合わせて曲線のばらつきを調べる。

最初の実装単位は、既知の短区間から採った3つの代表例を新しい短い歌詞に割り当て、時刻規則のみの版と比較するところまで。キー数だけを減らす最適化や、新しい学習モデルの導入は、この比較で見えた問題を根拠に判断する。

## 初回の実装と検証（2026-11-19）

編集モデルのワールド変形をフレームごとに評価し、流しは画面に対する位置差、横つぶれは横軸の長さの比、回転は区間始点からの連続角度として保存する。キー近似は既存の誤差制約付きフィッターを使い、区間端、値の極値、停止区間の端を固定する。生成時は行専用の親グループにキーを展開するため、歌詞の時刻規則と独立して適用できる。素材のID、リビジョン、SHA256と使用区間を各型に記録する。

## 文字別の適用と短寿命の追跡点検（2026-11-19）

- `glyphMotion:[{index,motion}]` は書記素の番号で適用先を指定する。番号は0始まりで空白を数える。本文の実際の字幅は共通の `layoutText` で測り、位置を持つグループと動きのグループを分ける。文字の `offset` はその文字の表示開始からの秒数。行の `motion` と合成しても、動きを外した比較版と登場順がそろう。合字部品には行の動きが作用し、文字別の動きは合体後の本文へ適用される。
- 7文字の「明日へ走り出す」で「明」に横つぶれ、「走」に回転、「す」に流しを適用。「明」から「す」までの最初の表示は76、77、79、80、81、82、83Fで行単位版と一致した。44フレームを計測したところ、最初は字間0.12倍で「出」と「す」の外接矩形が9フレームで最大約9px重なった。動きの振幅を固定し、字間を文字サイズの0.33倍にすると、はみ出しも外接矩形の重なりも0件になった。自動の字間補正は追加していない。
- `readingPosition` で読みを下・上・右から指定できる。大きく表示される「相」のルビは右へ移して、確認したコマで画面内に収まった。切り替え位置を手で選ぶため、再生中に読みの側が自動で切り替わることはない。
- 2フレーム以下の101ブロックから開始時刻とID順に5件ごとの21件を抽出し、元画像の前2〜後3フレームを目視した。10件で前後に同じ形が続く候補があり、1件は92Fの確定済みの交代、10件は局所の切り出しだけでは判定できなかった。連結先と誤結合率の確認は残っている。

再現は `node scripts/verify-motion-vocabulary.mjs p_mwm2iadqac02 p_mwm2i2tirjy0 data/Lyricsample1_Glyph_Motion_Output`。`line-and-glyph.mp4` の左は行単位だけ、右は文字別の動きを追加した版。`report.json` に文字別の監査結果、`short-track-audit.json` と画像3枚に追跡の点検結果を保存した。ブラウザからのローカル接続、独立評価、作業時間の比較、追加作品と実曲の検証は未確認。

## 1シーンの動きを抽象化して差し替える（2026-11-19）

4条件へのレビューでは、どの版も参照に近く見えず、動きのリニアさと、文中で一文字だけが動く理由が伝わらないことが指摘された。前回は末尾の文字へ抜けを直接指定し、合字には固定の寄せ方を使っていた。今回は検証対象を「食＋反→飯」の71–92Fに絞り、部品・読み・合字・反転・つぶれを同じ時間軸で再現した。
