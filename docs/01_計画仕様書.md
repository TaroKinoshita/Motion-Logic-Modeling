## 1. 何を作るか（要約）

参考のモーショングラフィックス／リリックモーション映像から、**動き・演出構成・音楽への反応のルール**を取り出し、別の曲・歌詞・素材で新しい映像を組み立てるための、AIが操作できる分析・制作アプリ。［確定］

最終目標は参考映像のコピーではなく「演出の選び方を別の条件でも使う」こと。そこへ至る検証可能な中間工程として、次の連鎖を一つずつ成立させる。

```
元動画 ──▶ 観察（計測）──▶ 単純化したシーン ──▶ 仮説・規則 ──▶ 新曲への割り当て ──▶ 新しいシーン
            何がいつ動いたか     図形で動きを再現       なぜ・どんな関係か     規則を別の曲に適用      描画・比較・出力
```

各矢印の右側は必ず**再生して見られる／数値で比べられる**ものにする。AIが「理解した」と文章を返すだけの段を作らない。

## 3. 技術選択

### 3.1 全体構成［決定］

**ローカルWebアプリ**として作る。TypeScriptの単一リポジトリで、アプリ本体（サーバー・UI・MCP・描画）を一つの言語にそろえる。Pythonは重い解析だけに使い、別プロセス・別環境に隔離する。

```
┌────────────── AIクライアント ──────────────┐        ┌──── 人 ────┐
│ Claude Code / Claude Desktop / Codex CLI    │        │  ブラウザ   │
└──────────────┬──────────────────────────────┘        └─────┬──────┘
          MCP (stdio)                                    HTTP + SSE
┌──────────────▼──────────────┐                              │
│ apps/mcp  MCPアダプター      │── HTTP ──┐                   │
│ （状態を持たない薄い変換層） │          │                   │
└─────────────────────────────┘   ┌──────▼───────────────────▼──────┐
                                  │ apps/server  Motion Logic サーバー │
                                  │  プロジェクト保存（リビジョン付き）│
                                  │  FFmpegで元動画のフレーム抽出      │
                                  │  シーンの描画（画像書き出し）      │──▶ data/projects/<id>/
                                  └──────┬─────────────────┬────────┘
                                         │ import          │ 子プロセス（今後）
                                  ┌──────▼──────┐   ┌──────▼────────────────┐
                                  │ packages/core │   │ workers/  Python解析   │
                                  │ スキーマ・評価 │   │ 研究実装ごとに別環境   │
                                  │ ・描画（共通） │   │ 入出力は共通JSON       │
                                  └──────▲──────┘   └───────────────────────┘
                                         │ import
                                  ┌──────┴──────┐
                                  │ apps/web  UI │
                                  └─────────────┘
```

要点：

- **状態の持ち主はサーバーだけ。** UIもMCPも同じHTTP APIを通る。だからAIの変更は即UIに出て、人の修正はAIから読める（引き継ぎ §8 の要件）。
- **描画コードは一つ。** `packages/core` の `drawFrame` を、ブラウザのプレビューとサーバーの画像書き出しの両方が呼ぶ。「UIで見えているもの」と「AIに返した画像」が別実装でずれる、という事故を構造的に防ぐ。
- **MCPアダプターは薄い。** ツール定義とHTTP呼び出しだけ。ロジックを置かない。

### 3.2 個別の選択と理由［決定］

| 対象 | 選択 | 理由 | 見送った案 |
|---|---|---|---|
| 配布形態 | ローカルWeb（ブラウザで開く） | 最短で動く。後からElectron/Tauriで包める | 最初からデスクトップ化：包装の手間が先に来る |
| 言語 | TypeScript（Node 24で直接実行） | ビルド工程なしでサーバー・MCPが動く。UIと型を共有 | サーバーをPythonに：描画コードをUIと共有できない |
| サーバー | Hono + @hono/node-server | 小さく、型が素直 | Express/Fastify：どれでも可、決め手は軽さ |
| UI | React 19 + Vite 8 | 標準的で次の担当が迷わない | |
| 検証 | Zod 4（未知キーは拒否） | AIの書き間違いを黙って捨てず、エラーで返す | |
| 描画 | **自作のCanvas 2D描画**（サーバー側は @napi-rs/canvas） | 下記 3.3 | Remotion、SVG+GSAP |
| MCP | 公式TypeScript SDK、**stdio** | 下記 3.4 | サーバーにHTTPのMCPを直付け |
| 保存 | プロジェクトごとのフォルダにJSON | 人が読める・差分が取れる・解析ワーカーと受け渡しやすい | SQLite：必要になってから |
| 解析 | Python別プロセス（uvで環境分離） | 研究実装は依存が衝突する。引き継ぎ §19 の方針どおり | 一つの仮想環境に全部入れる |

### 3.3 描画をRemotionにしなかった理由

引き継ぎ文書はRemotionを候補に挙げていた。検討の結果、初期は自作のCanvas 2D描画にした。

- 必要なのは「**宣言的なシーンJSONを、任意時刻 t で決定的に描く**」こと。これは `evaluateScene(scene, t)`（純粋関数）＋Canvas描画で足り、いま約250行。
- Remotionは「Reactコンポーネントをヘッドレスブラウザで撮る」仕組みで、1フレーム取得のたびにChromiumが介在する。AIが往復で何十枚も画像を取る用途には重い。
- 自作なら同じ関数がブラウザでもNodeでも動き、プレビューと書き出しが一致する。
- Remotionは3人以下の個人・組織は無料だが、それを超える組織は有償ライセンスが要る（公式FAQ）。将来の配布条件を縛る依存を、必須の土台には置かない。
- 捨てたわけではない。**高品質な最終書き出し**が必要になった段階で、共通シーン→Remotionのアダプターとして追加できる（AE/Blenderアダプターと同列）。

限界として認識していること：文字の描画はブラウザ（Chromium）とサーバー（Skia）でフォントの字形・字幅がわずかに違い得る。簡略版は矩形主体なので当面は許容するが、文字を精密に扱う段階で再評価する。

### 3.4 AIクライアントとの接続

| クライアント | 接続方法 | 状態 |
|---|---|---|
| **Claude Code**（デスクトップアプリのCodeタブ／CLI） | リポジトリ直下の `.mcp.json`（stdio） | **接続・往復を確認済み**（下記） |
| **Claude Desktop**（通常のチャット） | `%APPDATA%\Claude\claude_desktop_config.json` に追記（stdio） | 2026-11-15 に追記済み（`node` はフルパス）。**接続は未確認**（Claudeの再起動が必要） |
| **Codex CLI** | `~/.codex/config.toml` に追記（stdio） | 手順を README に記載。未実施 |
| **ChatGPTアプリ** | 公開HTTPSのリモートMCPが必要 | **初期対象外**（下記） |

［実測］MCPアダプターを公式SDKのクライアントから起動し、プロジェクト作成 → シーン更新 → 画像取得 → 元動画取り込み → 元動画と簡略版の比較画像取得、の往復が成立した。古いリビジョンでの更新と未知キーを含む更新は、理由つきのエラーで拒否された。

［実測］**実際のClaudeホストからの往復が成立した。** Claude CodeのCLI（2.1.289、`claude -p --mcp-config .mcp.json`、モデルはSonnet）をホストにして、MCPツールだけで次を行わせた：`get_guide` → デモプロジェクト作成 → 8コマのコンタクトシート取得 → `update_scene` で矩形の色を変更 → 単一フレーム取得 → 古いリビジョンでの更新。結果：

- モデルは画像の中身を実際に見られた。各コマの時刻ラベル（0.000s f0 … 5.000s f150）、矩形の数と色（白・白・黄）、3.5秒以降の黄色い輪の拡大を、シーン定義と矛盾なく説明した。
- 色を変更したあとの画像で、中央の矩形が緑に変わったことを画像から確認した。
- 古い `base_revision` での更新は理由つきで拒否された。

このとき出た指摘：複数コマのシート（1コマ320px）では色や細部の判別が単一フレーム（640px）より不確か／プロジェクトを削除するツールがない。

［実測］**デスクトップアプリのCodeタブのセッションからも接続できた。** 土台を作ったセッションでは、依存のインストール前にアプリが接続を試みて失敗し、そのセッション内では再接続できなかった（このアプリでは `/mcp reconnect` が使えない）。Claudeを再起動したところ接続され、`mcp__motion-logic__*` の10ツールが現れた。そこで `create_project` → `update_scene`（矩形の色を赤に）→ `get_frames` を行い、画像で赤に変わったことを確認した。初回セットアップでは `npm install` を済ませてからこのフォルダを開くこと。失敗状態が残ったときはClaudeの再起動で直る。

［未検証］Claude Desktop（通常チャット）での接続。設定は追記済み（バックアップ `claude_desktop_config.json.bak-mlm-20261115`）。CodeタブもClaude Desktopの一部なので、再起動するとこの作業セッションも切れる。そのため、確認はユーザーが再起動したあと、通常チャットで「motion-logic のツールでデモを作り、フレーム画像を見せて」と頼む形で行う。

**ChatGPTアプリについて。** 調査した範囲では、ChatGPTのMCP接続（開発者モード／カスタムMCP）は公開HTTPSのリモートサーバーが対象で、ローカルのstdioサーバーや localhost には直接つながらない。トンネルを使えば可能だが、「ローカル利用が基本・動画を外部へ出さない」という方針（引き継ぎ §8）と衝突する。したがって初期はClaude系とCodex CLIを対象にし、ChatGPTアプリ対応は「HTTPのMCPエンドポイント＋利用者が明示的に有効化するトンネル」として後で検討する。OpenAI側の仕様は変わりやすいので、着手時に公式資料で再確認すること。

**MCPの設計上の決めごと。**

- 画像は**MCPの画像コンテンツ**として返す。ファイルパスを返すだけにしない（引き継ぎ §7）。
- 複数時刻は1枚の**コンタクトシート**にまとめ、各コマに時刻とフレーム番号を焼き込む。AIが画像だけ見ても時刻を取り違えない。
- ツール一覧は小さく保つ（現在12ツール）。Claude Desktop（Windows）で大きなツール一覧が落ちるという報告があるため。詳しい説明は `get_guide` ツールで必要時に読ませる。
- 変更系ツールは `base_revision` 必須。人とAIの同時変更による上書きを防ぐ。
- 任意シェル実行やUI座標クリックのツールは作らない。

### 4.3 シーン形式（schema v2）［決定］

定義は [packages/core/src/schema.ts](../packages/core/src/schema.ts) が唯一の正。概要：

- 座標はpx・原点は左上。要素の `x, y` は**アンカー位置（既定は要素の中心）**。
- **計測時刻は秒（実数）**。v2では生成する動きに拍指定も使える。フレーム番号や拍に丸めて保存しない。元動画のフレームレートは `project.json` に有理数表記（例 `30000/1001`）のまま保持する。同期の「ずれ」は演出の特徴なので、保存形式が勝手に消さない。
- 要素：`rect` / `ellipse` / `text` / `group`（描画されない親。AEのヌル相当）。
- 変換：`x, y, scaleX, scaleY, rotation, opacity`。各値は固定の数値か、キーフレーム列。
- 補間：キーごとに `linear` / `hold` / `easeIn` / `easeOut` / `easeInOut` / `overshoot` / `anticipate` / `{cubic:[x1,y1,x2,y2]}`。すべて内部では3次ベジエ1種類で、AEの時間補間へ対応づけやすい。
- 親子：`parentId` で位置・回転・拡縮を合成。不透明度は継承しない（AEと同じ）。
- マーカー：`cut` / `beat` / `downbeat` / `section` / `note`。`origin`（`measured` / `estimated` / `manual`）で計測・推定・人手を区別する。

**わざと入れていないもの**（必要が実証されてから足す）：パス・ベジエ図形、マスク、ブレンドモード、粒子、カメラ／3D、文字単位アニメーション、モーションブラー、エフェクト。引き継ぎ §4 の表にある「粒子→点群・密度場」「カメラ→全体変換」は、Phase 2 で実素材を見てから表現を決める。カメラは当面 `group` を親にした全体変換で近似できる。

**2026-11-17 v2実装済み**：詳細は [05_M2a_Schema_v2_Design.md](05_M2a_Schema_v2_Design.md)、実測と制約は [06_v2_Implementation_Results.md](06_v2_Implementation_Results.md)。上の基本形式に次を追加した。

- `tempo: {bpm, offset}`、時刻の `{beat, offsetSeconds?}`。計測値・マーカー・scene.durationは秒を保持する。
- textの`split`、`stagger`、`unitTransform`、`letterSpacing`。全体transformを遅らせず文字単位の動きだけずらす。
- トラックの`repeat: {every, count? または until?}`。長さは秒か`{beats}`。
- `anchorX/anchorY`（中心原点のローカルpx、既定0）。x/yはアンカー位置。文字用`fontFamily`（現在MLM Arial 400/700）。
- v1を読み込み時にメモリ上で移行し、次の変更でv2保存。履歴のv1も復元可能。
- 文字単位アニメーションはv2で対応したため、上の「わざと入れていないもの」から除外する。

### 4.4 リビジョン［決定］

- プロジェクトごとに整数の `revision`。変更が確定するたびに1増える。
- 変更要求は `baseRevision` を伴い、現在値と違えば **409** で拒否する。呼び出し側は読み直してやり直す。
- すべての変更に `actor`（`human` / `ai` など）と `note`（何をなぜ）を記録する。
- 巻き戻しは「過去のシーンを新しいリビジョンとして復元」。履歴は消さない。

### Phase 1：元動画と簡略版を比べられる基盤 — **編集機能まで実装・検証済み。合成素材での受け入れ試験は実施（[03_1c_受け入れ試験結果.md](03_1c_受け入れ試験結果.md)）。実素材は未了**

できていること［実測］：動画の取り込み（パス指定／アップロード）、fps・長さ・解像度・音声有無の取得、元動画と簡略版の同期再生・停止・コマ送り・シーク、左右比較／重ね表示／簡略のみの切り替え、タイムライン（表示区間・キー時刻・マーカー・再生位置）、要素の選択と枠表示、要素のJSON編集、履歴と巻き戻し、**簡略版のキャンバス上でのクリック選択とドラッグ移動**、**簡略版のMP4書き出し**（元動画と同じフレームレート・元の音声つき、UIのボタンとMCPの `render_preview`）、**可変フレームレートの疑いの検出と警告**。

2026-11-15 に追加で確かめたこと［実測］（ブラウザで実際に操作し、保存結果をAPIで確認）：

- **拡縮ハンドル**（四隅）：ドラッグで `scaleX/scaleY` が等倍率で変わり、1リビジョンとして保存。
- **回転ハンドル**：ドラッグで `rotation` が変わる。画面上端に近い要素ではハンドルが画面外に出てつかめなかったため、その場合は下辺側に出すよう修正し、下側のハンドルで回転できることを確認。
- **親を持つ要素**（親が回転30°・2倍）の移動と回転：親のローカル座標に正しく変換されて保存（画面で右へ動かした量が、ローカル座標の計算値と一致）。親は変わらない。
- **タイムラインのキーのドラッグ**：キー時刻が変わり保存（例：1.0秒→1.504秒。ミリ秒で丸める。フレームには丸めない）。
- **イン／アウト（I・Oキー）、ループ、再生速度**：区間 1.003〜2.002秒、0.5倍で、再生位置が実時間の約半分の速さで進み、区間の終わりで始点へ戻ることを再生位置の記録で確認。
- **軌道表示**：選択中の要素の移動経路が線と点で表示される（見た目のみ確認）。
- **ごみ箱**：UIのボタン、HTTP API、MCPの `delete_project` のいずれでも `data/trash/` へ移動し、一覧から消える。
- **ファイル選択からのアップロード**：ファイル入力に動画を入れて change を起こし、取り込まれることを確認。OSのファイル選択ダイアログそのものは操作していない。
- **音声波形**：表示される（合成音の一定波形でのみ確認）。
- **書き出しの長さ**：簡略版・比較動画とも、区間を変えた8パターンを8回ずつ書き出し、64回すべてで期待どおりのフレーム数だった。比較動画の左半分（元動画）は指定区間の先頭と一致した（同時刻でPSNR 46dB、0.1秒ずらすと23dB）。

書き出しで見つけて直した不具合：

- `-shortest` で数フレーム短くなる → `-frames:v` で長さを決める（前回の修正。今回確認）。
- 比較動画が数〜十数フレーム短くなり、しかも**実行ごとに長さが変わった**。元動画と簡略版を1回のFFmpegで `tpad`＋`hstack` すると、入力の終わりの処理順で長さが揺れる（このFFmpegビルド単体でも再現）。元動画の区間を同じフレーム数のファイルとして単独で切り出し、ファイル同士を並べ、最後に音声を映像コピーのまま足す、という4段に分けた。
- 区間が元動画の終わり近くのとき、FFmpegが先に終了して `write EOF` で失敗した → 書き込み待ちの例外を握りつぶし、終了コードで報告する。
- OneDrive配下で同名ファイルを上書きすると、ときどき短いファイルになった → 一時ファイルに書いてから正式な名前へ置き換える。

UIで見つけて直した不具合：

- サーバーを再起動すると、開いている画面が以後の変更通知（AIの変更・削除）を受け取らなくなった（開発用プロキシが接続を開いたまま何も流さなくなるため。ページを再読み込みするまで直らない）。サーバーは10秒ごとにpingを送り、UIは25秒何も届かなければ接続し直して読み直す。サーバー再起動後、約13秒で一覧が更新されることを確認。

気づいたが直していない小さな点：

- アップロードで取り込んだときの履歴メモが元のファイル名でなく `source.mp4` と記録される。
- 再生速度などの選択欄にフォーカスがあると Space キーで再生できない（入力欄でのキー操作を妨げないための仕様。気になるなら変える）。

ドラッグ移動の仕様：位置がキーフレームのときは全キーを同じ量ずらす（軌道の形とタイミングは変えず、置き場所だけ移す）。親がある要素は、親の回転・拡縮を打ち消して親のローカル座標に直す。1回のドラッグが1リビジョン。

MP4書き出しの制約：同期処理で、一度に最大120秒。960×540・約3秒（89フレーム）で約0.3秒だった［実測］。数分の動画を一括で書き出すにはジョブ管理（Phase 2）が要る。

可変フレームレートの判定は簡易（ffprobe の `r_frame_rate` と `avg_frame_rate` が1%以上違えば疑いあり）。合成した可変フレームレート動画で検出できることは確認したが、取りこぼしや誤検出はあり得る。

残り（次セッション以降の作業、§7 参照）：

- 速度曲線のグラフ表示（軌道の点の間隔で速さは見える）。
- 狭い画面幅でのレイアウト（現状は横幅1000px程度以上を前提）。
- 実際の10秒程度の参考映像を使った手作業での再現。**これがPhase 1の本当の受け入れ試験**。合成テスト動画でしか確かめていない。

### Phase 2：分解と単純化の支援 — カット検出のみ実装

- **カット候補の検出は実装済み**［実測］。FFmpeg の `scdet`（画面全体の変化量）で検出し、`cut` マーカー（`origin: estimated`）として保存する。UIのボタン・HTTP API・MCPの `detect_cuts` から使える。1.0秒と2.0秒で切り替わる合成動画で、MCP経由で 1.0／2.0 秒を正確に返した。再実行すると前回の推定カットを置き換え、手動マーカーは残す。Pythonワーカーは不要だった。実素材でフラッシュや強い動きを誤検出しすぎる場合は PySceneDetect を検討する。
- ジョブ管理（進捗・キャンセル・失敗理由・成果物）。重い解析はここで初めて必要になる。
- Fast Sprite Decomposition と Motion Vectorization を**隔離環境で同じ短い素材にかけて比較**。8GBのVRAMに収まるかを最初に測る。
- 分割・追跡の補助として SAM 3.1 が端末に導入済み（§2）。新たなダウンロードは不要。まず短い素材でVRAMと速度を測る。
- 追跡結果 → キーフレームへの近似（計測値をそのままキーにせず、少数のキー＋イージングに当てはめる）。ここは自作部分。
- `observations.json` と `simplification.json` の導入。
- 比較の数値化（`compare_segment`）：位置・サイズ・登場時刻の差。
