# レビュー用の現状整理

ユーザーからレビュー用整理の依頼を受けた時点の記録。追加実装をいったん止める。

## 最も大きい問題

解析側では「観察→ブロックの動き→関係と時刻→文字と外観」という工程を作ったが、新曲の生成側に同じ工程を接続していなかった。

`Test_audio1_Production`と`Test_audio1_General_Planner`、`Test_audio1_General_Planner_v2`では、文字の寸法から配置候補を選び、文字要素へ直接変形キーを設定していた。先に独立したブロッキングを保存・検証し、その動きを引き継いで外観を作る工程はなかった。文字を塗りつぶして見せればよい、という問題ではなく、生成の中間表現と編集工程が欠けていた。

共通生成処理の文字サイズ・衝突・はみ出し検査は実装したが、これは演出の骨格の検証の代わりにはならない。この状態を目標へ十分近づいたかのように扱うべきではなかった。ユーザーに指摘されるまで、生成側の設計の逸脱を修正していなかった。

## 実行して確認したこと

- v2の元歌詞・別歌詞の各336コマで、文字の実測矩形の衝突とはみ出しは0件。これは読了・視線誘導・動きの良さの評価ではない。
- 32条件の範囲検査で24条件を生成、8条件を最低文字サイズ不足で拒否。同じ条件が重複する場合もあり、32本の独立した作品による評価ではない。
- 元歌詞と別歌詞で同じコードが動き、同じ入力では同じシーンになる。
- ブロッキング修正前に既存32テスト・型検査・Webビルドが通った。
- 下記のブロッキング修正後は型検査と32条件の範囲検査が通った。修正後の書き出し・既存テスト・Webビルド・HTTP・ブラウザ操作はまだ実施していない。

## 指摘後に変更したコード（未完了）

`apps/server/src/lyric-planner.ts`を変更中。現在は次の構造。

1. 語ごとの動きを持つgroupと、外形を示すrectを先に作る。
2. ブロックシーンと外観の対応を別に持つ。
3. `dressLyricBlocks`がrectを文字の子要素に置き換える。動きは親groupのキーを継承する。
4. ブロック用・文字用を別プロジェクトに保存するコードを追加した。
5. 編集したブロックの現在revisionから文字版を作り直すAPIとアプリ操作を追加した。

対象コードは `apps/server/src/lyric-planner.ts`、`apps/server/src/index.ts`、`apps/web/src/api.ts`、`apps/web/src/LyricPlanner.tsx`。HTTPは `POST /api/projects/:id/lyric-plan` と `POST /api/projects/:id/lyric-appearance`。

**この修正で新しいブロッキング動画はまだ生成していない。上のv2動画を、この修正後の成果として扱ってはいけない。** 型検査と範囲検査だけでアプリの一連の動作が完了したとも言えない。

まだブロック段階の承認を必須にせず、生成操作で両版を作る構造。語群全体の演出・関係の制約による選択・編集後の外形サイズに応じた文字の再フィット・別データでの品質評価も未完了。新コードは動きの所有先と外観適用の工程を分けるための修正で、動きの質が改善したことの証拠はまだない。

## 達成していないこと

- 参考作品に匹敵する新曲の完成品質。
- ブロックの段階で演出の流れを評価し、その結果を外観に反映する一連の実測。
- 歌詞の発音時刻を確認した同期。
- 参考作品から得た運動・構図・意味の関係を使う汎用的な演出選択。
- 作家判定の成立。調整後6/11、均衡55%、入れ替えp約0.37であり、作家性を捉えたとは言えない。
- 新曲生成の独立した人による品質評価。

配置候補・色・運動曲線・重みには設計者が決めた値が残る。背景反転も行番号の周期。これを学習した作家性とは呼ばない。

## レビューで確認してほしい境界

- ブロックが本当に動きのデータの持ち主で、外観がキーを作り直していないか。
- 解析で得た関係・動きの型と、生成の選択処理がどこまで接続されているか。
- 配置が安全なことと、演出の質が良いことを分けて評価しているか。
- 編集後のブロックから再生成する処理に、サイズ・寿命・削除・親子変更の取り扱い漏れがないか。

変更は未コミット。作業ツリーには今回以前の未コミットの分析・文書も含まれる。既存の全データが今回の修正から再生成されたわけではない。
