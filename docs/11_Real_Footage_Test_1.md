## 1. 素材と手順

- 素材：ユーザー提供の `C:\Users\kinos\Downloads\Lyricsample1.mp4`。1920×1080、24fps 固定、7.625 秒（183 フレーム）、AAC ステレオ。リポジトリには入れず、プロジェクト `p_mwl57hkcq4dc`（`data/`、Git 管理外）に取り込んだ。
- 内容：日本語のキネティック・タイポグラフィ（白地に黒、ほぼ無彩色）。漢字を部首に分けて組み合わせ、別の字にする言葉遊びが中心。
  - 例：田＋丁→町、食＋反→飯
  - ほかに、ローマ字のルビ、白黒の反転、カメラの流し・寄り、潰れた字形が戻る動き、散る点、文字の回転。
- 手順：AI として、次の順に進めた。
  1. MCP：`create_project` → `import_media` → `detect_cuts` → `get_frames` で観察
  2. HTTP：`detect-beats`、`track-region`、シーンの投入、`compare`、`measure-events`
  3. MCP：`update_scene` で修正
- この作業セッションの MCP アダプターは、起動時の古い版（12 ツール）のままだった。そのため、`detect_beats` / `model_project` / `compare_segment` は MCP から呼べず、同じサーバーの HTTP API を使った。ツールを変えたら Claude の再起動が要る、という運用上の注意として記録する。
- **位置と時刻はコンタクトシートからの目測**。字幅の計算も正解の流用もしていない（合成素材との違い）。

### 2.3 場面の切替と拍（M3 の measure-events）

場面が切り替わる 11 時刻（目測 7 件、カット検出 4 件）と、最寄りの推定拍との差を記録した。

- 差は −125〜+106ms。平均は −40ms（負＝映像が先）。拍の間隔は 476ms。
- 11 件中 9 件が ±100ms 以内。切替が拍に沿っている傾向は見える。
- 「映像が拍より約 90ms 先行する」件が 5 件ある。ただし、これが演出上の先行なのか、拍推定（librosa）の系統的な遅れなのかは区別できない。音の立ち上がり（onset）と照合する道具が要る。**仮説として保存はしていない。**

## 4. 見つかった不具合

1. **区間比較 API（`compare`）が、区間の端がフレームの境目にないと 422 になる。** 例：2.05〜2.95 秒（24fps で 21.6 フレーム）で、期待 22・実際 21。書き出し側は長さを四捨五入でフレーム数にし、元動画側はそれより 1 フレーム少なく切り出す。端を n/24 秒にそろえれば通る。24fps のような、秒の小数がフレームに乗りにくい素材で起きる。修正案は、書き出しの比較レイアウトと同じく元動画側の最後のコマを延ばすこと（`tpad`）。または、区間をフレーム境界へ丸めて結果に明記すること。
2. 比較スクリプトの誤りで、不要な「tmp」プロジェクトを 1 つ作った。ごみ箱へ移し済み。アプリの不具合ではない。

## 5. この試験で言えないこと

- 再現の「演出的な正しさ」。SSIM と比較画像の目視だけで、人の評価はしていない。
- 拍推定の精度（正解がない）。映像が拍に先行しているのか、推定が遅れているのか。
- M4（別の曲への適用）。2 曲目がまだないため、この素材では試していない。

## 6. 次の優先順位への示唆

合成素材の試験（文書 03）では「関係の記述」と「拍」が上位だった。実素材では、それに加えて次の 3 点が上位に来た。

1. **計測が効かない**（#2）。特徴点追跡は文字中心の素材に向かない。輪郭や二値化した領域の重心・外接矩形を使う方法を先に試す。白黒の素材ならこれで十分な可能性が高く、軽い。研究用の分解器や SAM 3.1 はその後。
2. **意味の層**（#1）。どの字がどの字の部品か、どの字にどのルビが付くか、という「文字の構成」を観察として記録できるようにする。これは M3 の仮説（「部首の組み合わせで言葉遊びをする」）の根拠になる。
3. **日本語フォントと字間**（#3・#4）。小さく確実で、SSIM にも直接効く。

あわせて、区間比較 API の 1 フレーム不具合（4 #1）は小さいのですぐ直せる。
