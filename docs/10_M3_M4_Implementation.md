# M3・M4 最小実用版の実装判断（2026-11-18）

追記：レビュー後の関係保持・複数区間・連動停止の修正は[文書11](11_Review_Relations_Fix.md)を参照。以下の初版の制限のうち該当箇所は更新済み。model保存も既定はIDごとの追加更新で、全置換にはmode:"replace"が必要。

ユーザーの「M3-M4まで進める」承認に基づく実装。M5は対象外。

まず計測成果物を履歴とつなぎ、M3では指定した映像イベントと最寄り拍の差を計測する。説明を自動的に事実とせず、仮説には観察ID、規則には仮説IDを必要とする。M4は明示した区間対応を使う。自動の楽曲構成理解は初版の対象外。

保存は observations / hypotheses / motion_rules / simplification / adaptation を別の文書として扱う。変更はcommitのbaseRevision検査を経由し、履歴へ文書のスナップショットも保存する。sceneスキーマv2は変更しない。巻き戻しはシーンと文書を一緒に戻す。旧履歴は文書なしとして扱う。

実素材が未提供なので、検証は合成素材で行う。実用性や演出の正解を確認したとは報告しない。

## 実装した範囲

### M2の接続

`POST /api/projects/:id/track-region`でFFmpegによるクリップ作成、offline/frozenの追跡ワーカー起動、生軌道とキー近似の保存、シーンへの矩形追加を一貫して実行する。元動画座標をシーン座標へ変換する。異なる縦横比やVFRの疑いは初版では拒否。最大10秒。観察には元プロジェクトID、revision、動画SHA256を残す。

矩形は追跡した領域の代理表現であり、文字認識・輪郭抽出ではない。不確かな追跡の停止理由とconfidenceを観察に保存する。親なしの新規要素なので既存要素を上書きしない。時刻・寸法の変換を曖昧にしないため、この制限から始めた。cubic-bezier近似と追跡を修正する専用UIは残る。

### M3

- `measure-events`：指定した映像イベントの秒時刻と、最寄りのbeatマーカーとの差を保存。負は先行、正は遅延。同距離は前の拍。イベントと拍のoriginをそのまま保持。拍を確定値へ自動変更しない。
- `model`：観察IDを参照する仮説、仮説IDを参照する規則を保存。採用済み仮説だけを生成に使用するが、acceptedは真偽の証明ではない。IDの不存在・重複を拒否。
- `variant`：hold（同値の連続キー間の停止長）またはstagger（文字の時間差）を変更した別プロジェクトを生成。元プロジェクトは変えない。規則を保存した時点のシーンSHA256と一致しない場合は再確認を求める。
- hold初版は当該トラックの後続キーだけをずらす。他の要素やプロパティを連動させるとは推論しない。繰り返しトラック・表示区間を超える変更は拒否する。全体のタメを表すには、どのトラックを連動させるかという規則の拡張が必要。

### M4

- `music`：120秒以内のローカル音声を黒背景・音声付きMP4に変換し、既存の再生と書き出し経路へ接続。別プロジェクトへの取り込みを想定。拍解析は既存detect_beatsを使用する。音声に実在する拍の精度は別評価。
- `adapt`：source/target区間、全要素の割当、変更理由を明示して生成。区間ごとに時間を一定倍率で変換し、位置・サイズ・イージングを維持。拍表記を秒へ解決して変換するため、元の規則文書・元revision・対応表をadaptationに残す。親子が異なる時間倍率になる割当は拒否。表示は割当区間でクリップする。
- `adapt-baselines`：全体尺だけ合わせる版、最初と最後の拍を合わせる版、固定demoテンプレート版を生成。拍基準版は両端の対応のみであり、不規則な全拍への局所リタイミングではない。
- 生成先に対象曲をコピーし、元動画との取り違えを避ける。素材や文字内容は保持する。文字数・レイアウトの自動最適化は未実装で、既存の編集操作で修正する。

## API / MCP / 画面

上記操作は `POST /api/projects/:id/<operation>`。文書の読取は `GET /api/projects/:id/documents`。変更にbaseRevision、M4はさらにtargetRevisionが必要。書き出し・画像取得には既存APIを使う。

MCPはツールを操作ごとに増やさず、`model_project(project_id, operation, input)`一つを追加した（合計15）。全入力形式はget_guideに記載。ロジックはサーバーにのみ置く。

専用フォームはまだない。API/MCPで生成し、生成された通常のプロジェクトを既存UIで確認・編集する。今回、既存UIの操作試験は追加していない。共通drawFrameによる画像とMP4出力で確認した。

## 検証済み

`node scripts/verify-modeling.mjs C:/Users/kinos/mlm_samples/kinetic_sample.mp4`

- 30msの先行、40msの遅延を符号付きで保存。
- 古いrevision、欠落した観察、規則保存後のシーン変更、古いtargetRevisionを拒否。
- 停止0秒・0.5秒・1.5秒の3版を生成。元のシーンとrevisionが変わらない。
- 文書とシーンを一緒に巻き戻し、再度復元できる。
- 8秒の合成音声の取り込みと拍ワーカー実行。試験音声は単音なのでBPM精度の検証には使っていない。M4の対応確認には明示した手動拍を使用。
- 6秒の参照シーンの前半3秒を5秒へ、後半3秒を3秒へ割り当て、生成キー時刻を確認。対象音声のSHA256一致、3種類の比較基準生成を確認。
- 生成結果を1秒・320pxで書き出し、ffprobeで30フレームと音声ストリームを確認。6時刻の生成画像も目視確認（前半の矩形群、後半の拡大する円）。
- MCP経由の領域追跡で21点の生軌道を保存し、y12キーの矩形をシーンへ適用。
- coreテスト23件、typecheck、web build、git diff --checkに成功。

成果物は `data/modeling-validation/report.json`、`adapted-frames.jpg`、各検証プロジェクト。データはgit管理外。

## 未完了と次の区切り

M3・M4の一連の処理がAPI/MCPで動く段階。実素材での受け入れ完了ではない。次は参考映像と別の実曲を用いて、手動イベント指定の負担、停止規則の適用範囲、区間端の不自然さ、文字数変更時のレイアウトを評価する。その結果からUIと規則の拡張を選ぶ。セクション自動推定、複数トラックにまたがるタメの規則、各拍への局所リタイミング、人による比較評価は残る。M5は着手していない。

保存は従来同様の複数JSON書込みであり、OS停止まで含む完全なトランザクションではない。文書読取は現在revisionの履歴スナップショットを正とし、同名JSONは閲覧用の写しにする。
