# Motion Logic Modeling（MLM）— Codex向け引き継ぎ

作成日：2026-11-14（日本時間）  
プロジェクト名：**Motion Logic Modeling**  
略称：**MLM**  
アプリ名：**Motion Logic**

この文書は、ユーザーとの企画議論、調査した公開情報、実装方針をまとめたもの。実装開始時にこの文書を読み、確定事項と提案を区別して進めること。今回行ったのは企画・Web調査・引き継ぎ文書の作成までであり、アプリ、モデル統合、リポジトリのダウンロード、実行性能の検証はまだ行っていない。

## 1. 最初に理解すること

作りたいものは、**参考のモーショングラフィックス／リリックモーション映像から、動き・演出構成・音楽への反応のルールを抽出し、別の曲・歌詞・素材で新しい映像を作るための、AI操作可能な分析・制作アプリ**。

参考映像の完全コピーや、文字・ロゴ・色だけの差し替えが最終目標ではない。コード化・再構成は理解を確かめる中間工程。その先の「演出の選び方を、別の条件でも使う」が目的。

例：

- 参考：文字を小さく反復させる → 時間差を詰める → 一瞬止める → サビで文字が飛び散る。
- 抽出したい規則：反復による期待 → 密度の上昇 → 抑制 → 強い変化による解放。
- 新作：図形の回転が連鎖する → 集まる → 止まる → サビでカメラが空間を抜ける。

上の新作は同じ軌道を使わなくてもよい。ただし、このような抽象的転用が自動で高品質に成立するかは未検証。開発で検証する対象である。

## 2. ユーザーが決めた方針

1. 名前はMotion Logic Modeling、通称MLM。アプリはMotion Logic。
2. 最初は絵柄・質感などのビジュアル作家性全体を扱わず、**動きと演出構成**に絞る。
3. 入力映像について「何を削り、何を残すか」を判断し、単純な色・形の映像へ落とす工程を重視する。
4. 単純化したコードから、動き・展開が残っているか再生して確認したい。
5. 別の音楽に応用するため、入力映像の音楽も解析し、映像との関係を扱う。
6. 解釈・推論には**ChatGPT／Claude**を使う。独自の大型VLM開発やQwen導入を初期の前提にしない。
7. ChatGPT／Claudeのデスクトップ側から、**MCPなどを介してアプリを操作**する構成を希望する。
8. アプリで入力、解析、途中経過、出力比較を確認・修正できるようにする。
9. 将来はAfter EffectsやBlenderなどにもつなげる。

ユーザーは率直で現実的な評価を希望。独自性、AIの理解、実現精度を誇張しないこと。既存モデルに可能なことと、今回自作することを明確にする。

## 4. 中心となる課題：演出を保つ単純化

単なる減色、ぼかし、輪郭抽出ではない。**見た目を削っても、動きや展開の効果を生む関係を残す**こと。

| 元の情報 | 削減案 | 必要なら残す情報 |
|---|---|---|
| 装飾文字 | 単純な文字・矩形 | 文字／単語単位、登場順、サイズ差、可読時間 |
| キャラクター | 輪郭・基本図形・少数パーツ | 向き、姿勢変化、シルエット、パーツ間の動き |
| 複雑な背景 | 大きな面・少数の層 | 空間配置、遮蔽、奥行き、視差 |
| 多色・質感 | 少数の色・単色面 | 主従のコントラスト、色が切り替わるイベント |
| 粒子・光・グリッチ | 点群・密度場・フラッシュ等 | 発生時刻、広がり、密度変化、持続時間 |
| カメラワーク | 全体変換／簡易カメラ | 移動、回転、拡大、視差、カット接続 |

単語が一括で動く場合と、一文字ずつずれて動く場合を同じ矩形一つにしてはいけない。粒子が盛り上がりを担うなら削除ではなく簡略表現にする。

単純化は一発で確定しない。元映像を保持したまま「候補を作る → 再生 → 失った関係を確認 → 必要な情報を戻す」を反復する。分析に先立って情報を不可逆に消す処理にはしない。

人の注目度や画像の目立ちやすさだけを、演出上の重要度と同一視しない。

## 5. 分析する範囲

| 層 | 記述対象 |
|---|---|
| 単体の動き | 軌道、速度、加減速、タメ、停止、オーバーシュート、回転、拡縮、透明度 |
| 要素間の関係 | 時間差、追従、連鎖、同期、主従、親子関係、重なり |
| カット接続 | 動きの引き継ぎ、方向反転、マッチ、ワイプ、連続／断絶 |
| 時間的構成 | 動と静、密度の増減、反復と変化、蓄積と解放 |
| 音との関係 | 拍、小節、アクセント、フレーズ、セクション、発声との対応とずれ |

音のすべてに動きを同期させるシステムにしない。同期しない選択、先行、遅延、静止も演出の特徴。

完成映像から、元の制作方法は一意には決まらない。拡大とカメラ接近など、画面上で似た結果を生む構造がある。元の内部構造の断定ではなく、編集・検証・再利用に適した説明を作る。

## 6. 授業Theoretical Modelingとの関係

ユーザーはRadboudのTheoretical Modelingを受講中。授業は、認知・心理についての言語的理論を形式化し、実装・シミュレーション・検証する内容。これをプロジェクトの考え方に利用する。

重要なのは、次を分けること。

1. **観察・計測**：何がいつ動き、音のどこに対応したか。
2. **説明仮説**：なぜその演出が選ばれ、どんな効果を生むと考えるか。
3. **実行可能なモデル**：変数・関係・制約として記述し、映像を生成する。
4. **検証**：条件を変えても関係が成立するか、別の説明に比べて有用か。

例：「サビ直前の0.4秒で動きが減った」は観察。「その抑制がサビの勢いを強めた」は仮説。両者を一つの確定事実として保存しない。

制作ルールをコードにしただけでは、人間の認知を説明する理論にならない。「タメがあると同じ後続動作を強く感じる」等について人の評価を調べるなら、授業に近い理論モデリング研究になる。

授業の教科書（内容は今回未読、ユーザー提供の参考リンク）：
https://computationalcognitivescience.github.io/lovelace/

授業文献：Cummins (2000)、Thagard & Verbeurgt (1998)、Hahn, Chater & Richardson (2003)。今回の映像への有効性がこれらで直接証明されているわけではない。

## 7. アプリと外部AIの役割

| 部分 | 役割 |
|---|---|
| ChatGPT／Claude | 映像解釈、単純化案、仮説、演出構成案、操作の計画 |
| Motion Logic | 読み込み、計測、データ保存、描画、比較、編集、ジョブ管理 |
| MCP層 | 構造化した操作の公開、結果・フレーム・状態の返却 |
| 描画エンジン | 共通データを簡略映像として再生・書き出し |
| AE／Blenderアダプター | 共通データを編集可能な制作物へ変換 |

アプリ内のAIチャットとAPIキー必須の構成を、初期の唯一の入口にしない。ユーザーは既存デスクトップAIを操作役にしたい。

ただし、**デスクトップ版なら必ず任意のローカルMCPへ接続できる、という仮定は置かない**。ChatGPT／Claude／Codexそれぞれについて、対象OS、バージョン、プラン、ローカル実行機能、MCPの接続先・transport、画像結果の扱いを実装時の公式資料と実機で確認する。通常のチャット、デスクトップアプリ、CLIは能力と権限が同じではない。

ローカルファイルパスをAIに返すだけで内容が見えるとも限らない。MCPの画像・リソース返却、低解像度のコンタクトシート、指定フレームの取得等を用意する。ホストが動画を直接読めなくても扱える設計にする。

## 8. 推奨する基本構造（設計提案）

まずローカルWeb UI＋バックエンド＋MCPアダプターで始め、必要になればデスクトップとしてパッケージする。

- UIとMCPは、同じプロジェクトサービス／データを操作する。
- AIが変更した内容はUIへ反映され、人の修正もAIが読める。
- 特定ソフトのスクリプトを唯一の保存形式にしない。
- プロジェクトの共通表現をJSON等で定義し、そこから各描画環境へ変換する。
- 自由なコード生成は補助に使えるが、基本図形と動きは検証できる宣言的データから描画する。
- 任意時刻の描画結果を再現できるようにし、比較に使う。
- 重い解析はジョブ化し、進捗、キャンセル、失敗理由、再開用成果物を残す。
- 動画全体の大量フレームを毎回AIに渡さず、カット単位・粗密の段階的取得・キャッシュを使う。
- ローカル利用を基本にする。クラウド公開や動画の外部アップロードを自動で追加しない。

ファイル形式の具体例（未確定）：

- `source_manifest.json`：入力メディア、fps、時間軸、ハッシュ。
- `observations.json`：計測した要素・動き・音イベント、根拠、確信度。
- `simplification.json`：残す／統合／置換／省略の判断と理由。
- `scene.json`：描画できる要素、階層、変換、曲線、カット。
- `hypotheses.json`：演出の仮説、支持例、反例、適用範囲。
- `motion_rules.json`：拍等を基準にした再利用可能な規則・制約。
- `adaptation.json`：新曲での割り当て、構成案、変更理由。

各段階の参照元、分析ツール／モデル、設定、スキーマバージョン、人の修正履歴を記録する。単に「AIが理解した」と表示しない。

## 9. UI要件

最低限、以下を表示・操作できるようにする。

- 元動画と簡略版の同期再生、停止、コマ送り、同一時刻へのシーク。
- 共通タイムライン：波形、カット、拍、動きの開始・停止。
- 選択した要素の枠・輪郭、ID、軌道、サイズ、必要に応じ速度曲線。
- AIの分析、単純化の理由、仮説、不確かな点。
- 「この二つを分ける」「一文字ずつ残す」「この効果を戻す」等の修正。
- ジョブ進捗、ログ、エラー、区間単位の再実行。
- 前バージョンへ戻す、簡略化候補A/Bの比較。

左右に元動画と出力、右側に分析、下にタイムラインという配置が候補。三列配置などの見た目そのものは未確定。

時間軸は元fps／PTSとの対応を保持する。拍に丸めて同期ずれを消さない。波形・検出拍は「推定」として手動修正できるようにする。

## 12. 音楽関連リポジトリ

### A. All-In-One — 基本候補

- Repo：https://github.com/mir-aidj/all-in-one
- Paper：https://arxiv.org/abs/2307.16425
- BPM、拍、小節頭、機能的セクション境界とラベル（intro／verse／chorus等）を推定し、JSON出力。
- 元実装にはNATTENなどの環境依存があり、特にWindowsはセットアップを要確認。
- 推定された区間・拍は正解とは限らない。UIで試聴・修正できるようにする。

### B. All-In-One-Infer — 元実装が環境依存で詰まる場合の候補

- Repo：https://github.com/openmirlab/all-in-one-infer
- 元のモデル／アルゴリズムを使い、現代的なPyTorchや純PyTorchの近傍attention等で導入を整理した推論用forkと説明されている。
- READMEの主張であり、今回の環境では未実行。元実装との結果互換性を短い素材で確かめる。

### C. MusiCue — まとまった音楽解析基盤の候補

- Repo：https://github.com/cedarconnor/MusiCue
- 音源分離、All-In-One、librosa等を組み合わせ、impulse／envelope／rampなどのイベント・曲線へ変換。
- READMEにはJSON／CSV／MIDI／AE JSX／TouchDesigner／Houdini／OSC／Unreal等への出力がある。
- AE出力の説明はNull＋Slider Controlのキーフレームとマーカー。映像全体のAE復元器ではない。
- フレーズ等の一部推定はヒューリスティック。音楽の意味を全面的に理解するモデルではない。
- 便利そうだが依存が多いため、最初から全機能を入れるかは比較して決める。

初期に必要なのは拍・音の立ち上がり・動的な強弱・セクション。歌詞の発声タイミングや意味は次段階にできる。既知の歌詞テキストを入力として使える設計にし、歌唱の文字起こしを唯一の入口にしない。

## 15. 自作する部分／既存を使う部分

| 部分 | 初期方針 |
|---|---|
| 動画の展開・フレーム取得 | FFmpeg等を利用 |
| カット・文字・分割・追跡 | 既存ライブラリ／研究コードを比較採用 |
| 動きのパラメータ化・曲線への近似 | 既存処理を参考に、必要な共通形式へ変換する実装 |
| 音楽の拍・構造 | 既存の事前学習済み解析を利用 |
| 単純化の判断 | ChatGPT／Claude＋自作の候補・検証ループ＋人の修正 |
| 演出仮説・ルール表現 | 自作。観察・仮説・生成規則を分離 |
| 新曲での構成 | 既存AIを使った自作の計画・制約・描画・比較ループ |
| UI・データ・MCP | 自作 |
| AE／Blender出力 | 共通形式からの変換を追加 |

既存部品をつなぐだけでは完成しない。一方、最初から巨大なモデルを訓練する必要もない。

## 16. 専用モデルを作る場合の位置づけ

初期版では専用モデルの事前学習を始めない。人が修正した単純化・分析・新曲への適用結果を蓄積し、失敗が明確になってから検討する。

候補：

- 単純化候補の順位付け。
- 残す要素・グループの選択。
- 動きの種類や時間的関係の分類。
- 音楽と演出イベントの対応付け。
- 新曲の区間に対する演出の選択・配置。

演出意図の正解ラベルが自然に得られるわけではない。合成シーンと既知の生成パラメータを使う評価、人による判断、実素材での評価を区別する。LLMの説明をそのまま学習の正解にして品質を循環的に保証しない。

## 17. 推奨する開発順と受け入れ基準

以下は提案。最終目標を保ちつつ、早く問題を切り分けるための順序。

### Phase 0：接続と描画の成立確認

1. 作業環境、既存ファイル、OS、GPU、FFmpeg、Node、Pythonを確認。
2. デスクトップAIからの実際のMCP接続方式を確認。
3. 最小アプリを立ち上げ、MCPから単純図形を一つ変更してUIに反映。
4. アプリの指定フレームをAIに返し、AIが見て状態を確認できることを試す。

受け入れ基準：人とAIが同じ状態を読み書きでき、画像を含む往復が一通り成立する。

### Phase 1：元動画と簡略版を比べられる基盤

- 10秒前後の文字・図形中心の2D映像を仮の初期対象にする。
- 読み込み、同期再生、コマ送り、区間指定、タイムライン、保存。
- 初期は手動指定した少数要素でもよい。単純図形で動きを再現できることを先に確認。
- 宣言的シーンからフレームと動画を描画する。

受け入れ基準：簡略版を実際に生成し、位置・サイズ・登場順・停止・カットの違いを確認して直せる。完成品に見えるUIだけで解析・描画が未接続、という状態にしない。

### Phase 2：分解と単純化を支援

- Fast Sprite DecompositionとMotion Vectorizationを隔離した環境で試し、同じ短い素材で比較。
- 必要ならOCR／SAM等を補助導入。
- AIに単純化案を提案させ、残す／統合／置換を編集可能にする。
- 不確かな追跡・分割を表示し、手動修正して再計算できるようにする。

受け入れ基準：動きの速度・順序・要素の対応が概ね保持され、修正結果を保存・再現できる。成立しない変形は明示する。

### Phase 3：音楽との関係と演出モデル

- 参考音楽の拍・区間・強弱と映像イベントを同じ時間軸に置く。
- 拍からの先行／遅延、反復、静止、密度変化を記述。
- 仮説と調整可能な規則を保存。
- タメなし／短い／長い等の比較版を生成。

受け入れ基準：AIの説明に対応する計測・生成結果が存在し、変数変更の結果を比較できる。

### Phase 4：別曲で構成し直す

- BPMや区間構成の異なる新曲を入力。
- 元の時刻やカット順の固定コピーに依存せず、規則を新曲へ割り当てる。
- 新しい素材、文字数、区間長に対応し、変更理由を表示。
- 単純な全体速度変更／ビートへのリタイミング／固定テンプレートと比較。

受け入れ基準：動作が壊れないだけでなく、参考のどの関係を保持し、何を変えたか追える。演出的な良さは人の評価も必要。

### Phase 5：AE等への編集可能な出力

- まず対応範囲を限定してレイヤー・キーフレームへ変換。
- 単なるMP4貼り付けを、編集可能な出力と称さない。
- アプリ内プレビューとの差、未対応項目を報告する。

## 18. 評価の考え方

単純化が目的なので、画素誤差だけで最適化しない。

- 計測：位置、サイズ、方向、速度、停止、登場順、遮蔽の変化。
- 時間的関係：要素間の時間差、同期、反復、カット時刻。
- 音楽との関係：拍・発声・区間との対応、意図した先行・遅延。
- 構成：密度、動静、反復と変化、展開の配置。
- 再利用：曲や文字数を変えても成立するか。
- 人の評価：元の緩急が残るか、新曲で効果的か、直す手間が減るか。

簡略版で動きと展開が残るか、新作が単なる素材差し替え／速度変更を超えているかは別々に評価する。元映像一つだけから作家性や演出意図を断定しない。

## 20. 次のCodexへの具体的な依頼

この文書の目的に沿ってMotion Logicの実装を始めてほしい。

最初に、(1)実環境と既存作業の確認、(2)対象AIクライアントからのMCP接続の実証、(3)プロジェクト共通データと最小描画経路、(4)元動画と簡略版の同期比較を優先する。
